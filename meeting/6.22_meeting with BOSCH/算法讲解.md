可以。这里的“地面 outpainting”容易误解：**它最初不是用 AI 把地面画出来**，而是一个 **temporal reprojection / real-pixel rendering** 算法。

也就是说，它的目标是：

> 当前这一帧车底/车身附近地面看不到，但车过去或之后某一帧可能看到了同一块真实地面。我们把那一帧的真实地面像素投回来，补到当前 ERP panorama 的底部。

可以把它理解成“从时间里借真实地面”，不是“凭空生成地面”。

**整体流程**

```
当前 panorama 中下半球有黑洞 / 车身遮挡
        ↓
找出这些需要补的 bottom/nadir ground pixels
        ↓
把每个 ERP pixel 反投影成 3D 地面点
        ↓
去整段 AV2 log 里找哪些历史/未来帧看过这个地面点
        ↓
把这个 3D 地面点投影到那些 source camera 里
        ↓
过滤掉被 ego 车身 / 动态物体挡住的 source
        ↓
用多个 source 验证颜色是否一致
        ↓
选择最可信的一个真实 source pixel 写回当前 panorama
        ↓
对极低分辨率 nadir 区域低通 / abstain
```

下面逐个讲组件。

**1. ERP / Nadir Cap**
ERP 是最终 360 图，宽度表示水平 360°，高度表示上下视角。

`nadir` 是最底部，也就是“看向车底/地面”的方向。AV2 的 ring cameras 装在车顶前部，不是真的向正下方看，所以 ERP 底部通常是：

- 黑洞
- 车身/hood/车尾遮挡
- 很斜角看到的地面
- 几乎没有高质量纹理

算法第一步就是找这些需要补的区域。代码里是 `blackg` / `capg`，大意是：当前 composite 里还是黑的，或者 ray 穿过 ego body 的下半部分，就认为它属于 ground fill candidate。对应 [db89_ghost_recovery.py (line 1037)](/D:/BaiduSyncdisk/2024 to future/koi chen/experiments/Waymo2Panorama/scripts/phase3/db89_ghost_recovery.py:1037)。

**2. Ray / 反投影**
每个 ERP pixel 对应一个 3D 方向 ray。比如底部某个 pixel 表示：

```
从虚拟相机中心 C 出发，朝下方某个方向看
```

如果我们假设它看到的是地面，就可以让这条 ray 和地面相交，得到一个 3D ground point。

最早可以用简单平面：

```
z = ground_height
```

后来发现平面不够，因为路面有坡、curb、坑、路沿，所以加了 LiDAR ground height：用 LiDAR 附近点估计那个地方真实的 ground z。对应 [db89_ghost_recovery.py (line 1049)](/D:/BaiduSyncdisk/2024 to future/koi chen/experiments/Waymo2Panorama/scripts/phase3/db89_ghost_recovery.py:1049)。

这个组件的作用是：**把“我要补哪个 pixel”转成“世界中哪一个地面点”。**

**3. Ego Pose**
AV2 每一帧都有车在世界坐标中的位置和朝向，也就是 ego pose。

为什么需要它？因为同一块地面，在当前帧看不到，但车开过去之后，另一个时刻的相机可能看到了。要判断“历史帧的 camera 有没有看到当前这个地面点”，必须知道历史帧车在哪里。

这就是 temporal reprojection 的基础：

```
当前帧 ground point X_city
→ 换到 source frame 的 ego 坐标
→ 再换到 source camera 坐标
→ 投影到 source image 像素
```

**4. Candidate Frame Selection**
最初失败的一个点是：候选帧按时间选，比如 ±60 frames。看起来合理，但如果车在红灯停了 9.5 秒，时间很近，几何位置没变，仍然看不到车底地面。

所以 Fable 5/v8 改成：

```
whole-log geometry search
```

也就是先看车实际移动了多少米，而不是时间差多少。

原则：

- 太近：还是被自己车身挡住。
- 太远：视角差太大，曝光变化大，地面点可能不可见。
- 合适：大概 5-58m displacement 里找候选。
- 每个 displacement bucket 选时间最近的几个 frame。

这对应 progress 里 DB-93 的关键修正：固定时间窗口失败，改成 whole-log geometry search。见 [progress.md (line 45)](/D:/BaiduSyncdisk/2024 to future/koi chen/experiments/Waymo2Panorama/agent/progress.md:45)。

这个组件的作用是：**找“可能看过这块地面”的历史/未来帧。**

**5. Camera Projection**
找到 source frame 后，要问：

> 这个 ground point 在 source frame 的哪个 camera 里？落在图像哪个 pixel？

这需要 camera intrinsics / extrinsics：

- intrinsics：相机内部参数，比如 focal length、principal point，用来把 3D camera coordinate 投影成 2D pixel。
- extrinsics：相机相对 ego vehicle 的位置和朝向。

如果投影结果在图像边界内，且深度 `z > 0`，说明这个 camera 方向上“可能看到了它”。代码里 `px2/py2/z2/okq` 就是在做这个事，见 [db89_ghost_recovery.py (line 1127)](/D:/BaiduSyncdisk/2024 to future/koi chen/experiments/Waymo2Panorama/scripts/phase3/db89_ghost_recovery.py:1127)。

这个组件的作用是：**把世界地面点映射到 source image 的真实像素。**

**6. EMC / Exposure-Time Pose**
AV2 的 ring cameras 不是完全同一瞬间曝光。比如某些 camera 早 12.5ms，某些晚 22.5ms。

如果车在动，高速时 20ms 已经能移动几十厘米。对地面重投影来说，这会导致同一个 stripe 被投到不同位置。

所以 source camera 不能用统一 timestamp 的 pose，要用每个 camera 自己的 exposure-time pose。这叫 EMC，ego-motion compensation。

它的作用是：**避免因为相机曝光时间错开导致地面纹理多重错位。**

代码里 source frame 加载后用 `fr2.timestamps_ns[ring_cams[ci2]]` 取每个相机自己的 capture-time pose，见 [db89_ghost_recovery.py (line 1175)](/D:/BaiduSyncdisk/2024 to future/koi chen/experiments/Waymo2Panorama/scripts/phase3/db89_ghost_recovery.py:1175)。

**7. Ego Self-Occlusion / 两盒模型**
这是很重要的部分。

source camera 看向某个地面点时，可能射线先撞到 source vehicle 自己的 hood、车顶、车尾。那 source pixel 看起来可能是白色 hood 反光，而不是地面。

早期如果没有挡掉这个，会出现：

```
hood sky reflection 被当成 road
→ 地面变蓝/白/紫
→ 看起来像 outpainting 失败
```

所以 Fable 5 加了 ego self-occlusion gate。

最开始用一个大车盒，但太保守，会把合法视角也挡掉。后来改成 two-box：

```
full-length low body box: hood + trunk，比较低
short cabin-height box: cabin，比较高
```

这个组件的作用是：**防止把 source vehicle 自己的车机/hood/车身反光当地面。**

对应 [db89_ghost_recovery.py (line 1138)](/D:/BaiduSyncdisk/2024 to future/koi chen/experiments/Waymo2Panorama/scripts/phase3/db89_ghost_recovery.py:1138)。

**8. Dynamic Object Gate**
source frame 里可能有车、行人、自行车。我们要补的是 static ground，不是把 source frame 的车贴到当前地面上。

所以算法用 AV2 annotations / boxes 去过滤 source frame 里的 moving objects。代码里 `fboxes` 和 `blocked` 就是做这个。

这个组件的作用是：**防止动态物体颜色进入静态地面层。**

不过这里也是现在暴露问题的地方之一：box/annotation 不是完整 visibility model，未标注静态车、反光、source-side first-hit 仍然会漏。

**9. Six-Source Consensus**
对一个地面点，算法最多保留 6 个候选 source samples。

为什么不直接平均？因为如果 6 个 source 有轻微错位，平均会把 lane line / curb / asphalt texture smear 掉。

所以它的策略是：

```
1. 收集多个 source 颜色
2. 计算 median color
3. 看每个 source 距离 median 多远
4. 选 nearest-to-median 的那个真实 source pixel
```

median 的作用是“验证一致性”；nearest-to-median 的作用是“最终仍然用一个真实像素，不 blend”。

这个组件的作用是：**用多视角互相投票，但最终保持 source-faithful。**

对应 [db89_ghost_recovery.py (line 1188)](/D:/BaiduSyncdisk/2024 to future/koi chen/experiments/Waymo2Panorama/scripts/phase3/db89_ghost_recovery.py:1188)。

**10. Source Agreement / Spread Gate**
如果多个 source 对同一个 ground point 的颜色差很多，说明它们可能不是在看同一个真实表面，或者 grazing angle 太极端。

代码里计算 `spread`：

```
spread = source colors 相对 median 的平均偏差
```

如果 `spread` 太大，就不相信这个点，不强行画真实纹理。

这个组件的作用是：**发现“source 们互相不一致”的危险点。**

DB-98 里黑色 streak 就是这个机制暴露出来的：有些 near-nadir 点只有极斜视角，source 互相不同意，硬画就出 radial streak。对应 [db89_ghost_recovery.py (line 1190)](/D:/BaiduSyncdisk/2024 to future/koi chen/experiments/Waymo2Panorama/scripts/phase3/db89_ghost_recovery.py:1190)。

**11. Truth-Ring Cast Correction**
极斜角看地面时，asphalt 会反射天空，尤其晴天会偏蓝/紫。这个不是纯 bug，是物理现象：grazing Fresnel reflection。

但如果直接放到 ERP 底部，会和上面较正常角度的路面颜色不连贯。

所以算法从当前 panorama 底部边界附近找一圈可信 road pixels，叫 truth ring，用它的 median 颜色估计一个 global gain，把填充地面色调拉回附近路面。

这个组件的作用是：**让补出来的地面颜色和当前图边界更一致。**

对应 [db89_ghost_recovery.py (line 1203)](/D:/BaiduSyncdisk/2024 to future/koi chen/experiments/Waymo2Panorama/scripts/phase3/db89_ghost_recovery.py:1203)。

**12. Resolution-Matched Low-Pass**
这是 CV 里很核心的思想：不要显示超过证据分辨率的细节。

near-nadir 地面只被 4-6° grazing view 看到。这个角度下，一个 camera pixel 对应地面上很长一条区域。它本来就没有高分辨率地面纹理。

如果你把它硬渲染成 full-res ERP，会出现：

- speckle
- radial streak
- 拉伸纹理
- 假 lane/curb 结构

所以 Fable 5 加 row-weighted low-pass：越靠近 nadir，越平滑。progress 里写得很清楚：它不是 invent detail，而是不要假装 4° grazing pixel 有 full-res detail。见 [progress.md (line 55)](/D:/BaiduSyncdisk/2024 to future/koi chen/experiments/Waymo2Panorama/agent/progress.md:55)。

这个组件的作用是：**把真实地面显示在它真实可观测的分辨率上。**

**13. Low-Coverage Warning / Observability**
算法还记录：

- candidate frames 有多少
- displacement 范围
- coverage 百分比
- 是否 low coverage

这些不是为了好看，是为了知道这个地面填充到底有没有证据。progress 里称为 observability baked in，见 [progress.md (line 59)](/D:/BaiduSyncdisk/2024 to future/koi chen/experiments/Waymo2Panorama/agent/progress.md:59)。

这个组件的作用是：**防止算法偷偷编造成功。**

**用一句更直观的话总结**
Fable 5 的地面 outpainting 像这样：

```
不是画家：
“这里缺地面，我来想象一个地面。”

而是侦探：
“当前帧这里看不到，但车 20 米前/后有没有真的看过这块地面？
如果看过，哪个相机看得最清楚？
这个像素是不是被车身/行人/hood 挡了？
多个来源是否互相同意？
证据分辨率够不够？
不够就别假装。”
```

**为什么当时单帧看起来成功**
因为这套算法对单张 anchor 很强：

- whole-log 找到了看过地面的帧。
- two-box ego gate 去掉了明显 hood contamination。
- multi-source median 过滤了一些异常 source。
- low-pass 让最底部不再乱。
- 5 个 scene coverage 达到 94-100%，视觉上可接受。见 [progress.md (line 57)](/D:/BaiduSyncdisk/2024 to future/koi chen/experiments/Waymo2Panorama/agent/progress.md:57)。

**为什么现在视频暴露问题**
因为连续 93 帧会经过更多几何状态。某些 frame 里：

- target ray 先撞到近处车，不应该画 ground。
- source ray 先撞到 source ego hood，不应该采样。
- source frame 里有静态车/未跟踪物/反光物。
- near-pole blind spot 只有极低 grazing evidence。
- 每帧独立选 source，错误会随时间跳动。

所以现在的问题不是主 seam，也不是普通 inpainting，而是：**原始 ground fill 还不是完整的 visibility-consistent renderer。**

下一步 DB-101 要补的正是这个缺口：target-side first visible surface + source-side first visible surface。也就是更严格地问：

```
这个 ERP ray 看到的第一个东西真的是地面吗？
这个 source camera 看到这个 ground point 时，中间真的没有别的东西挡住吗？
```
